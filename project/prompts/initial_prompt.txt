WORKFLOW (execute in this order)

Phase 0 — Discovery (do this before generating any program)
  a. Parse the JSON and RTF to produce a complete inventory of tables:
     titlekey, table id, title, population, dataset(s) needed, row/statistic list.
  b. Run PROC CONTENTS (or dictionary tables) against ADSL, ADAE, ADTTE, ADPC
     to capture actual variables, types, lengths, and formats.
  c. Cross-check every variable named in the JSON/RTF against the actual
     datasets. Build the variable-mapping table described below before
     writing any table program.

Phase 1 — Per-table program generation
  For each table in the inventory:
  a. Create one SAS program named exactly <titlekey>.sas in the `prog` directory.
  b. The program must render exactly one PDF named <titlekey>.pdf, written to
     the same `prog` directory as the SAS program, and must never open,
     append to, or overwrite another table's PDF.
  c. Include the standard header (see below).
  d. Perform the table's own inline validations (dataset/variable existence,
     record counts, population/treatment-arm counts, missing values,
     duplicate participant checks) and write its rows to the shared
     validation dataset using PROC APPEND (or equivalent) rather than DATA
     step overwrite, so concurrent/successive program runs never destroy
     each other's validation rows.
  e. If a required variable cannot be resolved (see mapping rules below),
     mark the table ERROR, log the unresolved variable and affected
     rows/statistics, skip PDF generation for that table only, and continue
     to the next table.

Phase 2 — Consolidated validation report
  After all table programs are generated/described, produce (or describe how
  each program contributes to) one combined validation dataset/report at:
     G:\gsi_stds\dss_2026\s0000000\final\draft1\tools\val_report.out
  containing, per row: titlekey, dataset name, variable name, validation
  check, expected condition, actual condition, status (PASS/WARNING/ERROR),
  and validation message.

VARIABLE-MAPPING RULES
- Preserve CDISC variable names and metadata labels wherever possible.
- Never invent variables, values, analysis flags, treatment groups, or rules.
- If a shell-referenced variable is missing but a demonstrably equivalent
  variable exists in the ADaM dataset, map it and document the mapping
  (source variable → target variable → justification) in the validation report.
- If no defensible mapping exists, mark the table ERROR and do not generate
  its PDF (see Phase 1e).

- Use stable sorts; preserve the shell's row order exactly.
- Do not suppress zero-count categories unless the RTF programming notes
  explicitly permit it.
- Never hard-code a displayed value — every number must be derived from the
  ADaM data at run time.

DEFENSIVE PROGRAMMING REQUIREMENTS
- Check &SYSERR after key steps; check for missing datasets/variables before use.
- Verify ODS PDF opened/closed successfully; verify the output directory exists

- Guard against accidental duplicate counts (e.g., unintended many-to-many merges).
- Emit clear, actionable SAS log messages for every failure path.
- Set a per-table return-status macro variable (e.g., &&TITLEKEY&_STATUS) that
